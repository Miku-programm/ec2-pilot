# API contract for implementation

Same-origin FastAPI backend, cookie session auth. JSON errors `{detail: string}`. All times ISO UTC; UI renders local. No secrets in API responses. API paths start `/api`.

- GET health -> `{ok,version,setup_required}`
- POST setup/login `{password}` -> `{ok:true}` plus HttpOnly session cookie; POST logout.
- GET state -> `{accounts:[],scripts:[],monitors:[],results:[],activity:[],probes:[],eip_cleanup:[],meta:{default_region,server_time}}`.
- accounts: `{id,name,aws_account_id,arn,region,access_key_hint,created_at}`. POST accounts `{name,access_key_id,secret_access_key,session_token?,region?}` validates with STS; omitted region defaults to `us-east-1` (also exposed as `meta.default_region`). Saved accounts retain their region. DELETE accounts/{id}; GET accounts/{id}/instances -> `{instances:[]}`.
- instance: `{id,name,state,instance_type,public_ip,private_ip,availability_zone,image_id,launch_time,key_name,security_group_ids:[],subnet_id,elastic_allocation_id?}`.
- Instance listing only calls `DescribeInstances`, not `DescribeAddresses`. Its network-interface association response does not contain `AllocationId`, so the current adapter does not fill `elastic_allocation_id`. A public IP without that optional field has an unknown address type, never inferred as auto-assigned. Missing ID in the rotation dialog means not queried, not no EIP; only the rotation backend's fresh `DescribeAddresses` result decides old-address release. No public IP is shown separately from unknown address type.
- GET accounts/{id}/resources -> `{images:[],subnets:[],security_groups:[],key_pairs:[]}` (optional launch helper). Images include `id,name,description,architecture,root_device_name`; newest up to 5 Amazon Linux 2023 images per architecture (`x86_64` and `arm64`). UI filters suggestions for T4g ARM64 and T2/T3 x86_64.
- POST accounts/{id}/instances/launch `{name,image_id,instance_type,subnet_id?,security_group_ids:[],open_all_ports:true,key_name?,user_data?,script_id?,volume_size:8}` -> `{instance_ids:[],message}`. Required `Idempotency-Key` header: 16–64 letters/digits/hyphens; retain the same value for a retry of the same request.
- Launch checks AMI architecture against AWS `DescribeInstanceTypes` supported architectures before `RunInstances`, including manually entered AMI/type values. Requires `ec2:DescribeInstanceTypes` permission. Architecture mismatch or unavailable architecture metadata prevents creation.
- `open_all_ports` defaults true: create a dedicated security group in the subnet VPC or default VPC with all inbound protocols/ports for `0.0.0.0/0` and `::/0`. Cannot combine true with explicit security group IDs. False uses provided groups, or AWS default group when empty. Never edits provided groups. Operation token determines group name and ownership tags, so retries reuse it; failed instance launches retain this group. Security group preparation failure prevents `RunInstances`.
- POST accounts/{id}/instances/{instance_id}/start|stop|reboot `{}` -> `{message}`.
- PUT accounts/{id}/instances/{instance_id}/user-data `{script_id?,user_data?}` -> `{message}`; requires stopped instance. Existing user data update does not guarantee rerun.
- POST accounts/{id}/instances/{instance_id}/rotate-ip `{release_previous:false}` -> `{public_ip,allocation_id,previous_allocation_id?,previous?,tagged,message}`; manual allocate/associate EIP, old EIP release opt-in and only if owned+safe; IPv4 is billable.
- Old-EIP release queue (`release_previous:true` only; false remains the manual/API/new-monitor default): a `blocked` intent with the old AllocationId, AssociationId, AWS account, region and unique rotation attempt is persisted before AllocateAddress. Persistence failure prevents allocation; only confirmed AssociateAddress success moves that attempt to `queued`. Interrupted or ambiguous results remain blocked for verification.
- Cleanup processing holds a renewable owner lease, re-reads the address before ReleaseAddress, waits while the recorded AssociationId persists, and moves to `review` (no automatic release) on another association or unclear state. Retries back off; 10 unsuccessful rounds lead to `failed`. This cap applies only to old-EIP cleanup, never scheduled IP rotation. A stale owner cannot finish, delete, or modify a replacement intent. Built-in scheduler and `app.cron_worker --once` run the same persistent queue; graceful shutdown waits for started cleanup work.
- GET state includes `eip_cleanup:[{allocation_id,association_id,public_ip,network_border_group,instance_id,attempt_id,account_id,aws_account_id,region,state,processing,attempts,last_error,next_try_at}]`. `processing` reflects an active cleanup lease or an active rotation associated with that instance. UI shows account/region, distinguishes live processing from results awaiting verification, and refreshes after mutations or conflicts. No background discovery of unrelated EIPs.
- DELETE eip-cleanup/{allocation_id} keeps the address; POST eip-cleanup/{allocation_id}/approve re-queues `blocked`/`failed` rows after admin verification. Both return 409 while cleanup or the related rotation is active. Accounts with cleanup rows cannot be deleted; account existence, intent persistence, and deletion checks are transactionally coordinated. Pre-allocation cleanup contention skips a scheduled rotation without treating it as an ambiguous AWS mutation.
- AWS ReleaseAddress can disassociate an in-use address in a default VPC. AWS offers no atomic conditional "release only if still detached" operation: fresh reads and panel leases do not eliminate races with external AWS operations, and no time bound is claimed for that gap. Preserve the default `release_previous:false` when external ownership changes must remain entirely under manual control. Newly allocated-address rollback after a definite rejected association remains separate from this old-EIP queue.
- scripts: `{id,name,content,created_at}`; POST scripts `{name,content}`; PUT/DELETE scripts/{id}.
- monitors: `{id,name,account_id,instance_id,port,interval_seconds,timeout_seconds,samples,enabled,next_run_at,last_status,last_checked_at}`; POST monitors same sans generated fields; PUT/DELETE monitors/{id}; POST monitors/{id}/run -> `{result}` (check only, no automated rotation or failure-streak accumulation). Bounds interval 60..86400, timeout 1..10, samples 1..5. Target is current public IPv4 of selected owned EC2 instance, never arbitrary host input.
- Scheduling: `schedule_type` interval|cron (old missing -> interval; new UI -> cron), `cron_expression` default `*/5 * * * *` exactly five fields, `timezone` default Asia/Shanghai. Optional Linux `app.cron_worker --once` reuses the backend due-task worker; set web `PANEL_SCHEDULER=external` for OS crontab.
- Rotation policy: `auto_rotate:false`, `rotation_trigger` tcp_failure|suspected_filtering, `failure_threshold:3` (1..20), `release_previous:false`. Scheduled checks only; there is no cooldown or daily/rolling-24h attempt cap. Schedule, consecutive-failure threshold and fresh preflight verification determine eligibility for each attempt. Runtime fields `failure_streak`, `failure_ip`, `rotation_status`, `rotation_message`, `last_rotation_at`. Atomic reservation and resource locks are keyed by actual AWS account+region+instance. Errors/interrupted attempts pause rotation until POST monitors/{id}/reset-rotation, returning `{ok,message}`; reset clears the failure streak and preserves operation history. A possibly running interrupted operation must be at least 15 minutes old before reset; this is an in-progress uncertainty guard, not a routine cooldown.
- Saved legacy `cooldown_seconds` and `max_rotations_per_day` settings are removed on migration. Existing operation history remains available.
- Scheduled results optionally have `rotation:{status,message,old_ip?,new_ip?,verification?}`; active statuses skipped,threshold,recovered,rotated,awaiting_review. Verification uses the same observation shape as a check and never recursively triggers replacement. A later scheduled round may rotate again once its consecutive-failure and preflight conditions are met, without an additional delay or attempt-count cap. Historical results may retain the retired cooldown/daily_limit statuses.
- `recovered` is a legacy status key meaning preflight cancelled rotation: the target may have recovered, changed IP, or lacked sufficient failure evidence (including a read/probe error). The UI labels it neutrally as “复检未触发换 IP”, not confirmed recovery. The existing policy still clears the failure streak and does not allocate an EIP in these cases.
- result: `{id,monitor_id,monitor_name,instance_id,target_ip,port,checked_at,status,success_count,samples,latency_ms,loss_percent,gfw_status,summary,observations:[]}`; status reachable/unreachable/no_public_ip/error; gfw_status insufficient_evidence/suspected_filtering/reachable_from_both/unreachable_from_both; no conclusive GFW verdict.
- probes: `{id,name,region_type,url,enabled}`; region_type mainland/overseas; POST probes `{name,region_type,url,token}`; DELETE probes/{id}. POST remote `/probe` accepts `{target_ip,port,timeout_seconds,samples}` with Bearer token (24–512 non-whitespace ASCII characters); samples <=5, timeout <=10, rejects non-public IP. Probe URL must be HTTPS public host, no redirects; root app handles validation.
- activity: `{id,action,message,created_at,level}`.

UI Chinese dark polished dashboard with accounts, EC2 list/actions, script library, TCP monitor/history, probe settings. Add-account must not call contact API. UI confirmations for instance mutations and visible EIP cost/restart/user-data caveats; prevent duplicate clicks. Any demo is explicitly labeled, isolated, read-only and never calls mutation APIs.
